BAGIAN 1

Ikhtisar & Nilai Tambah Sistem SIM PBB SIDOMULYO

Laravel 11 • MySQL 8 • Midtrans & DANA
Studi Kasus Lapangan

Pemerintah Kampung Sidomulyo, Kec. Punggur, Kab. Lampung Tengah. Karakteristik agraris di mana 1 Wajib Pajak umumnya memiliki lebih dari 1 bidang NOP (rumah, sawah, ruko, kebun).

Pilar Nilai Tambah
  • Portal Publik Cek NOP + Masking NIK (UU PDP)
  • Pembayaran QRIS DANA Bisnis + Alur Verifikasi
  • Fleksibilitas Cicilan & Otomasi 4 Triggers SQL
  • Parser Impor Massal DHKP CSV & Rekap Dispenda
Konteks Demonstrasi UTS

Seluruh data tagihan demonstrasi disetel ke Rp 1.000 per ketetapan untuk memfasilitasi pengujian alur pembayaran di ruang kuliah tanpa risiko finansial.

Matriks Perbaikan Kelemahan Penelitian Sebelumnya:
No Celah Sistem Terdahulu Solusi Inovasi yang Diterapkan pada SIM PBB Saat Ini Manfaat Operasional Lapangan
1 Warga & NOP Digabung (1NF/2NF Rusak) Pemisahan entitas wajib_pajak dan objek_pajak (Relasi 1:N 3NF). Nama warga tidak perlu diketik berulang untuk pemilik banyak bidang tanah.
2 Tidak Ada Histori Multi-Tahun Entitas tagihan_sppt dengan composite unique key (nop, tahun_pajak). Dapat melacak riwayat pelunasan dan tunggakan lintas tahun anggaran.
3 Tidak Mendukung Cicilan Pencatatan total_terbayar, sisa_tagihan, dan status Belum Lunas / Cicilan / Lunas. Mengakomodasi petani yang membayar pajak secara bertahap saat panen.
4 Konfirmasi Bank Tanpa Verifikasi Penerapan Approval Workflow: Menunggu Verifikasi → Terverifikasi / Ditolak. Mencegah manipulasi bukti transfer palsu atau mutasi rekening fiktif.
5 Input Manual Ribuan Baris DHKP Modul parser impor massal berkas CSV DHKP dan tabel log_import_dhkp. Ribuan ketetapan dari Dispenda terunggah otomatis dalam hitungan detik.

Matriks Integritas Foreign Key & Kardinalitas Relasi:
Parent Table Child Table Kardinalitas Foreign Key Field Action Rules (ON UPDATE / DELETE)
wajib_pajak (id_wp) objek_pajak (id_wp) 1 : N (One-to-Many) objek_pajak.id_wp CASCADE / RESTRICT (Data WP tidak bisa dihapus jika memiliki NOP aktif)
objek_pajak (nop) tagihan_sppt (nop) 1 : N (One-to-Many) tagihan_sppt.nop CASCADE / RESTRICT (Objek tanah tidak bisa dihapus jika memiliki riwayat SPPT)
tagihan_sppt (id_sppt) transaksi_pembayaran (id_sppt) 1 : N (One-to-Many) transaksi_pembayaran.id_sppt CASCADE / RESTRICT (SPPT terjaga selama ada catatan transaksi bayar)
users (id_user) transaksi_pembayaran 1 : N (One-to-Many) transaksi_pembayaran.id_petugas_verifikator CASCADE / SET NULL (Jika akun petugas dinonaktifkan, riwayat verifikasi tetap utuh)

Activity Diagram (3 Alur Bisnis Utama)

Swimlane Multi-Aktor
Alur 1: Pembayaran QRIS DANA Bisnis & Verifikasi Admin
Real-time Polling & Auto-Redirect

Menggambarkan interaksi menyeluruh: Warga memindai QRIS Rp 1.000, mengirim bukti transfer, halaman berpindah ke mode tunggu dengan interval polling tiap 3 detik. Admin memeriksa rekening mutasi DANA Bisnis, menyetujui transaksi, trigger database memotong tagihan, dan browser warga secara otomatis beralih ke struk kasir berhasil tanpa reload manual.

Alur 3: Impor Massal DHKP (Spreadsheet CSV dari Dispenda)
Bulk Processing & Audit Trail 
flowchart TD
    A([Awal: Dispenda Kirim File DHKP Tahunan]) --> B[/Admin Unggah File CSV via Form Impor/]
    B --> C{Validasi Format Berkas & Header Kolom}
    C -- Format Salah / Rusak --> D[Tampilkan Pesan Error: Format Kolom Tidak Sesuai] --> B
    
    C -- Format Valid --> E[Buka Transaksi Database: DB::beginTransaction]
    E --> F[Inisialisasi Counter: Sukses=0, Gagal=0]
    F --> G[Loop: Baca Baris per Baris CSV]
    
    G --> H{Apakah NOP Sudah Terdaftar di objek_pajak?}
    H -- Belum Ada --> I[Catat Error: NOP Belum Terdaftar di Master Objek] --> J[Gagal + 1]
    
    H -- Terdaftar --> K{Cek Apakah SPPT Tahun Tersebut Sudah Ada?}
    K -- Belum Ada --> L[INSERT tagihan_sppt Baru] --> M[Sukses + 1]
    K -- Sudah Ada --> N[UPDATE Nilai Pokok Ketetapan] --> M
    
    J --> O{Masih Ada Baris Berikutnya?}
    M --> O
    O -- Ya --> G
    O -- Tidak (Selesai File) --> P[(Catat Hasil ke log_import_dhkp)]
    P --> Q[DB::commit]
    Q --> R[/Tampilkan Halaman Rekapitulasi: Jumlah Sukses & Gagal/] --> S([Selesai])

State Machine 1: Siklus Status Tagihan SPPT

Transisi status tagihan dihitung secara otomatis oleh trigger basis data: 

stateDiagram-v2
    [*] --> Belum_Lunas : SPPT Diterbitkan (Terbayar = 0)
    
    Belum_Lunas --> Cicilan : Bayar Sebagian (0 < Terbayar < Total)
    Belum_Lunas --> Lunas : Bayar Penuh Sekaligus (Terbayar >= Total)
    
    Cicilan --> Cicilan : Tambah Setoran Cicilan Berikutnya
    Cicilan --> Lunas : Setoran Terakhir Melunasi Sisa Tagihan

Kamus Data & Otomasi Triggers SQL

Spesifikasi Fisik & Integritas SQL
Logika Operasional 4 Database Triggers (Penjaga Integritas ACID):
Trigger 1: trg_sppt_before_insert

Menghitung otomatis saat SPPT baru diterbitkan:
total_tagihan = pbb_terhutang + skp + stp + denda
sisa_tagihan = total_tagihan - total_terbayar
Status awal: Belum Lunas.

Trigger 2: trg_sppt_before_update

Menghitung ulang total tagihan dan sisa tagihan jika nilai pokok/denda diupdate. Mengubah status secara otomatis menjadi Lunas jika total_terbayar >= total_tagihan, atau Cicilan jika total_terbayar > 0.

Trigger 3: trg_pembayaran_after_update

Saat status verifikasi transaksi berubah menjadi Terverifikasi, trigger langsung menambah total_terbayar dan memotong sisa_tagihan pada tabel tagihan_sppt.

Trigger 4: trg_pembayaran_after_insert

Jika pembayaran tunai langsung diinput di loket balai kampung dengan status Terverifikasi, trigger langsung memperbarui saldo tagihan SPPT secara atomik tanpa intervensi manual di controller PHP.
